# LeadFlow

Multi-tenant lead generation SaaS. Each client gets an isolated workspace, finds businesses
through the official Google Places API or CSV import, and keeps a compliance-first
do-not-contact list.

## Status: backend pipeline works end to end (up to approved drafts)

- Auth (register/login, JWT, argon2 password hashing)
- Workspaces: every table is scoped by `workspace_id`; cross-tenant access returns 404
- Campaigns (niche, location, offer)
- Lead sources: Google Places search, CSV import (deduped, 5 MB cap)
- Email enrichment: finds contact emails on lead websites (SSRF guard, robots.txt, junk filter)
- AI lead scoring 0-100 with reason (Gemini; output validated, prompt-injection fenced)
- AI email drafts: LLM writes only the message; signature, postal address and unsubscribe
  link are added by code, so they can't be forgotten or edited out. Links, fake "Re:"
  subjects and unfilled placeholders are rejected. Edit/approve flow; editing resets approval.
- Public unsubscribe link (signed token; GET confirms, POST unsubscribes) + suppression list
- Alembic migrations, with a test that fails if models and migrations drift apart
- Dashboard (`frontend/`, Next.js): sign in, campaigns, the whole pipeline in one page, draft
  review with an exact-email preview, a two-step send, and settings. The API token lives in an
  httpOnly cookie, and the proxy to the backend is allow-listed. Plain, Vercel-style design with the Circuit Teal brand used sparingly. See `frontend/README.md`.
- 223 backend tests + 111 frontend unit tests + 27 browser (Playwright) tests. Compliance, drift,
  sending and frontend security guards were each mutation-tested (break the code on purpose,
  confirm a test fails).
- Eval harness for AI scoring (`backend/evals/`): labelled leads, ranking metrics, held-out set,
  run history. See `backend/evals/README.md` for results and caveats

- Sending from the client's own mailbox over SMTP: SMTP passwords encrypted at rest (Fernet),
  SSRF-guarded host/port checks, **dry-run by default**, daily cap per mailbox, opt-out list
  re-checked right before each send, claim-before-send so a draft can never go out twice,
  stops on login/network errors, suppresses refused addresses, auto-pauses a mailbox when too
  many addresses are refused, `List-Unsubscribe` (+ One-Click over HTTPS) headers

## Not built yet (sending limits)

- **No real bounce handling.** We see addresses refused during the SMTP conversation. Most
  bounces arrive later as email; reading them needs IMAP access to the mailbox.
- **No pacing.** Sends go out back to back (max 20 per request). Human-like spacing needs a
  background worker.
- **No DKIM/SPF/DMARC check** of the client's domain, no warm-up, no open/reply tracking.
- **SMTP only.** Gmail/Microsoft OAuth is not implemented (SMTP app passwords work).
- **Cold email is not transactional email.** Do not point this at SES/Postmark/SendGrid: their
  policies generally forbid unsolicited mail and they will suspend the account. Send from the
  client's own mailbox, a few dozen a day, from a domain with proper DNS records.
- Real sending has only been tested against a local capture server, never a real mail provider.

## Run locally (backend + dashboard)

```bash
# terminal 1: backend
cd backend && python3 -m venv .venv && . .venv/bin/activate && pip install -r requirements.txt
alembic upgrade head && uvicorn app.main:app --reload          # http://localhost:8000/docs

# terminal 2: dashboard (needs Node 22+)
cd frontend && cp .env.example .env.local && npm install && npm run dev   # http://localhost:3000
```

Backend only:

```bash
cd backend
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
python -m pytest -q
alembic upgrade head               # create/update the database tables
uvicorn app.main:app --reload      # http://localhost:8000/docs
```

With Docker (Postgres): copy `.env.example` to `.env`, then `docker compose up --build`.

## Database migrations

The schema is managed by Alembic. The app no longer creates tables itself.

```bash
alembic upgrade head                                  # apply pending migrations (safe to re-run)
alembic revision --autogenerate -m "add foo to leads"   # after editing a model
alembic downgrade -1                                  # undo the last migration
alembic check                                         # do the models and the database agree?
```

Rules that save you later:
- **Read every autogenerated migration** before committing it. Autogenerate misses things such as
  column renames (it sees a drop plus an add, which loses the data).
- Adding a `NOT NULL` column to a table that already has rows needs a `server_default`, or the
  migration fails on real data.
- Never edit a migration that has already been applied anywhere. Write a new one.
- Run `pytest`: `tests/test_migrations.py` fails if you changed a model and forgot the migration.
- A database created before Alembic existed: `alembic stamp head` marks it as current without
  re-creating tables (this is how the original dev database was adopted, data intact).
- Constraints get predictable names from a naming convention in `app/db/session.py`. Keep it:
  SQLite can't alter anonymous constraints.

## Trying sending without emailing anyone

```bash
python -m aiosmtpd -n -c aiosmtpd.handlers.Debugging stdout -l 127.0.0.1:1025   # prints mail, delivers nothing
# in .env (dev only): ALLOW_PRIVATE_SMTP=true  and  ENCRYPTION_KEY=<a Fernet key>
# then POST /mailboxes with smtp_host 127.0.0.1, smtp_port 1025, security "none"
```

`POST /campaigns/{id}/send` is a dry run unless the body says `"dry_run": false`.

## Before production

- Set a strong random `SECRET_KEY` (the default is a placeholder) and an `ENCRYPTION_KEY`
  (back it up: losing it makes every stored mailbox password unreadable)
- `ALLOW_PRIVATE_SMTP` must stay false, or clients can aim the server at your internal network
- Cold email must include sender identity, a working unsubscribe, and honor the suppression list (CAN-SPAM / GDPR)
